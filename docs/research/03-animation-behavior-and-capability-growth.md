## 13 November correction — code-created characters, economical acting, optional rig complexity

**DECIDED:** In Cutroom v2 **no image-generation or video-generation models** make character poses or animation frames. LLMs produce drawing and motion **code** (SVG/Canvas/HTML/CSS/TS, procedural vector/raster via conventional graphics, authored sprite/pose definitions and puppet control). Cutroom begins with a **brief**, decides how characters look and moves them; prepared assets from a user are optional. Reuse the same character's **accepted code/asset revisions** as style/reference context for subsequent poses, motions and shots.

**DECIDED:** Optimize for **clear, non-janky, style-appropriate communication**, not maximum physical realism. A simple silhouette/pose change, prop translation, staged reaction, camera or audio cue may convey a handoff better than IK. If a particular scene needs precise hands/contact/arms, select richer IK/rig/structured channels or experiment. Animation methods are chosen adaptively per situation; sophisticated earlier research remains available but not mandatory.

**DECIDED:** Code-rendered visual components are the default. A character might be SVG code with several parameters, a sprite sequence constructed by code, or a rigged puppet; dynamic capability creation means writing/adapting **code and conventional 2D assets**, not calling a diffusion image/video model. A flat component can be an acceptable rendering asset with limited internal editability; do not require elaborate capability manifests for a trivial action. Preserve stable semantic identity, local time, exposed controls when present, and source revision/visual-reference linkage. Planning can use provisional character/scene anchors before final visual frames.

**OPEN:** exact consistency metrics between code-authored poses, generic rig-control interface, when to request deeper editability, animation blend rules and detailed asset shape. See [HLD entry](../HLD-ENTRY.md), [spatial/async contract](07-production-coordination-futures-and-spatial-contracts.md), [versioning](08-versioning-lineage-and-experiment-memory.md).

## Current research direction — adaptive animation and behavior (12 November 2026)

**DECIDED DESIGN INTENT:** A missing animation capability is **not automatically grounds to reject the production request**. If the requested behavior makes sense and is permitted, the harness should attempt a **capability-repair/generation workflow** before declaring it unresolved. Earlier notes referring to unsupported actions should be read as a **planning diagnostic**, not an immediate final refusal. A deterministic final compiler must still refuse to execute an unresolved action rather than hallucinating controls.

**DECIDED DESIGN INTENT:** Renderer/animation-method selection must be **dynamic and evidence-guided**. The harness can use a growing registry of behavior implementations and renderer/method experience, and it may call an Experiment Agent to test fresh candidates. The registry is an evidence-backed starting point, **not a static rulebook or a ban on experimentation**.

**RESEARCH CANDIDATE:** separate a requested **semantic behavior**, a **method proposal** (rigged 2D IK, pose atlas, puppet, sprite sequence, procedural motion, hybrid), a **validated capability/asset package**, and a **frozen resolved animation**. This means `hand_object(alice,bob,document)` cannot be treated as an implicit promise that the selected character assets already support a handoff.

### The adaptive method choice for a handoff

| Candidate method | Promising when | Risks to inspect |
|---|---|---|
| 2D puppet + IK and anchors | Both characters have suitable arm chains/targets; grip and contact need precision | IK alone does not create good acting; reachability, joint distortion, style mismatch |
| Authored sprite/pose sequence | Handcrafted exchange looks cleaner, or a rig is visually inappropriate | Need sufficient poses and consistent character/prop identity; less flexible timing/view |
| Mixed technique | Character body controlled by sprites while a hand/prop uses articulated layers | Attachment continuity, masks/occlusion, interpolation, editability |
| Code-authored/retargeted performance | Missing poses/controls can be created through SVG/drawing code, sprites generated by conventional rendering, or accepted motion tools | Inconsistent views, appearance drift, quality verification and rights |

**Illustrative workflow:**

```text
1. Director requests: Charlie hands document to Alice.
2. Semantic validator checks goal, actors, document identity and constraints.
3. Capability lookup: compare known rig controls, reach anchors, pose atlases and prior outcomes.
4. Planner proposes feasible candidate methods: IK, sprites, hybrid, or newly prepared pose assets.
5. If uncertain: orchestrator commissions Experiment Agent to evaluate variants on a branch.
6. If missing: authorize Capability Producer to generate/extend the needed poses, rig or clips.
7. Validate new assets and action contract; test 2D contact, prop attach/release, legibility.
8. Critique short renders; select an acceptable method and version its capability package.
9. Freeze resolved animation for deterministic compilation and actual video rendering.
```

This is a research **proposed behavior** of the future system; no self-extending agent, IK rig synthesizer or evaluation benchmark exists in Cutroom yet.

### Dynamic Action & Technique Registry — proposed entry

```yaml
action_recipe:
  id: interaction.handoff_document
  version: 4
  semantic_tags: [handoff, contact, prop_transfer]
  method: puppet_ik_2d       # alternatives can coexist with same semantic action
  required_actor_capabilities: [wrist_anchor, arm_chain, reach_target]
  required_object_capabilities: [attachable, shared_2d_transform]
  preconditions: [giver_has_document, receiver_reachable]
  postconditions: [receiver_has_document, giver_released_document]
  reads: [actor_poses, prop_transform, film_time, layer_order]
  writes: [arms, wrist_anchors, document_attachment, contact_events]
  compliance_tests: [reachability, attach_release_no_jump, scene_readability]
  evidence: [candidate_render_ids, reviewer_notes, tested_asset_versions]
  status: candidate_validated  # not a universal guarantee
  implementation_ref: scoped_versioned_recipe
```

The registry should support candidate versions, confidence/evidence and context qualifiers (character style, rig topology, camera/shot scale, duration and quality criteria). A generally good IK strategy may be poor for an expressive 2D silhouette. It should not bake in global rules such as `handoff -> IK`.

### Capability growth is different from renderer fallback

- **Available capability:** use it after validation, or explore a better variant if expected quality warrants comparison.
- **Missing but generatable capability:** synthesize a view/pose/rig/animation, or adapt an existing character asset; verify and register an appropriately scoped new version.
- **Unsupported method, feasible alternative:** select a different representation or technique *without silently losing required creative semantics*.
- **Unknown feasibility:** isolate an experiment, gather evidence and report uncertainty.
- **Impossible/conflicting constraint:** explain the conflict; do not endlessly retry or override locks.
- **Unresolved after bounds:** return a structured choice to the creator/harness with reasons and evidence rather than a fake success.

**Safety and correctness:** Experimental changes must not mutate the accepted character package or production. External assets and model-generated code require provenance, permissions, sandboxing and tests. A new action may change downstream timing, contact or layer dependencies; it needs impact analysis and a new revision. Runtime self-extension during a frame render is **not** part of the chosen direction.

### Research questions before HLD/LLD

1. How should capability features, pose anchors, IK affordances, masks and character views be standardized across sprite, vector, puppet and programmatically created assets?
2. Who owns publishing a tested recipe into the registry, and can the harness reuse provisional recipes without creator approval?
3. Which metrics tell a convincing handoff from merely satisfying contact geometry (popping, foot sliding, expression, readable action, style)?
4. When should experimentation be skipped due to cost or obvious existing evidence, and when should the Experiment Agent try alternatives?
5. Can a generated action be adapted to a different character topology, or must it be character-specific? How do failures affect confidence?
6. What is the minimum conformance proof before a new action is executable in a frozen Render IR?

# Part V — Intensive research track 3: Animation, characters and 2D performance synthesis

## 11. Rendering a character is easy relative to *directing* one

The source assets and the ability to draw them do not imply a convincing performance. The hard problem is converting high-level choices—`nervous`, `deadpan`, `double-take`, `hesitate`, `stumble`, `interrupt`, `look-at`, `reach`, `hand-off`—into temporally coordinated, emotionally readable gestures. We should distinguish **motion execution** (known mechanical problem), **motion authoring** (artistic/representational problem), **performance resolution** (choosing a feasible actual take), and **performance evaluation** (checking what viewers see).

### 11.1 Representation families within 2D

| Type | Internal model | Strengths | Limits |
|---|---|---|---|
| Cutout / rigid sprite | one textured quad + transform | Very simple movements, easy independent alpha layer | No internal articulation; rotations reveal flatness |
| Sprite sheet / pose atlas | ordered named frames + pivots | Reliable hand-drawn acting, mouth and expression variants | Must author/generate sufficient frames; interpolation between poses limited |
| Layered puppet | head/torso/limbs/eyes/mouth groups and pivots | Independent facial/body controls, transforms, reuse | Requires character preparation, rigging, joint aesthetics |
| Bone/skinned mesh 2D | bones, weights, IK, constraints, blended animations | Continuous articulated motion, reusable clips | Setup and interactions are hard; movement can look rubbery |
| Vector character | paths/shapes + parametric geometry | Crisp scale, programmable expressions, procedural animation | Hard for highly detailed acting; shape morphing constraints |
| Frozen/generative clip | actual prerecorded animation/video | Rich appearance without authoring every pose | Internal object-level editability is limited unless tracking/masks/alternative views exist |

**The scene can mix them.** A vector balloon, sprite crowd, layered puppet presenter and video background remain one 2D production. This is not a reason to add 2.5D/3D immediately.

### 11.2 Existing animation research and technology

- **Rive**: state machines with typed inputs, blend states and layers; useful reference for combining action states and expressions. Its runtime/editor semantics and licensing need a concrete evaluation.
- **Spine**: extensive 2D skeletal animation runtimes, timelines, stateful `AnimationState`, blending, multiple tracks and procedural skeleton control. Its runtime licensing depends on Spine licensing; not a free default dependency.
- **Live2D Cubism**: 2D model/animation and Web/native SDKs; commercial distribution terms require separate review. Its strength is rich character movement from layered artwork, but that doesn't solve semantics or asset generation for us.
- **Lottie**: layer, precomposition, timing and keyframe conventions; useful for low-level declarative animation and export/interchange thinking.
- **Synfig**: mature open-source 2D vector animation application; useful conceptual and implementation research for tweening and scene authoring.
- **MediaPipe Face Landmarker**: expression blendshape output from visual input, potentially a **motion/reference analysis** source rather than a complete performance generator; licensing, bias, mapping and reliability must be examined.

Primary refs: [Rive state machines](https://github.com/rive-app/help-center/blob/master/runtimes/state-machines.md), [Rive blend/layers](https://github.com/rive-app/help-center/blob/master/editor/state-machine.md?plain=1), [Spine Runtimes](https://en.esotericsoftware.com/spine-runtimes), [Spine applying animations](https://us.esotericsoftware.com/spine-applying-animations), [Live2D SDK](https://www.live2d.com/en/sdk/about/), [Live2D license](https://www.live2d.com/en/sdk/license/), [Lottie](https://lottie.github.io/lottie-spec/latest/specs/layers/), [Synfig documentation](https://wiki.synfig.org/), [MediaPipe Face Landmarker](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker).

### 11.3 Earlier StykAnimate source review — useful 2D reference, **not** a selected dependency

The retired 29 October 2026 `STYKANIMATE-RESEARCH.md` reported inspection of [`filippocalippo/StykAnimate-App`](https://github.com/filippocalippo/StykAnimate-App) at commit `def97214c2b491fbce82647f625a73f78416c6d8`. For current 2D research, its relevant observed design patterns were **stable figure identity, definition/instance separation, layered timelines, sprite/rig posing, IK and pinned endpoints, reusable nested animation clips, parallax, and time-based scene evaluation shared by editor, playback and export**. These are research references for our potential actor model, scene graph and animation compiler, not proof that its internals can be reused directly.

The earlier review reported **43 passing upstream tests** from its IK and attached-movieclip-mesh suites. Those tests were narrow; they did **not** measure artistic quality, production speed, end-to-end rendering, automatic agent control or export reliability. It found internal programmatic editor interfaces, but **did not establish a supported external agent API or unattended production interface**. Its declared `GPL-3.0-or-later` license and third-party notices require legal/technical review before any source reuse. Source pointers from that historical review: [architecture](https://github.com/filippocalippo/StykAnimate-App/blob/def97214c2b491fbce82647f625a73f78416c6d8/docs/ARCHITECTURE.md), [IK](https://github.com/filippocalippo/StykAnimate-App/blob/def97214c2b491fbce82647f625a73f78416c6d8/docs/inverse-kinematics.md), [editor interfaces](https://github.com/filippocalippo/StykAnimate-App/blob/def97214c2b491fbce82647f625a73f78416c6d8/src/editor.mjs), [license metadata](https://github.com/filippocalippo/StykAnimate-App/blob/def97214c2b491fbce82647f625a73f78416c6d8/package.json).

**Retained research question:** would our own typed, versioned 2D action/pose language gain more from borrowing these editor and evaluator concepts, versus compiling into a supported existing animation runtime? No engine or license decision has been made.

## 12. The performance lowering problem

**High-level performance instruction:** `presenter reacts 650ms after the eruption with a restrained double-take, without interrupting the selected speech recording`.

Possible *resolved action*:

```yaml
performance_take:
  actor: presenter
  action: double_take
  version: take_07
  trigger: eruption.start
  offset: 650ms
  duration: 460ms
  channels:
    gaze: [{at: 0ms, target: camera}, {at: 80ms, target: volcano}]
    head_rotation: [{at: 0ms, deg: 0}, {at: 160ms, deg: 18}, {at: 260ms, deg: 6}]
    facial_expression: [{at: 0ms, name: neutral}, {at: 140ms, name: unsettled}]
    upper_body: [{at: 0ms, pose: idle}, {at: 240ms, pose: recoil_small}]
  reads: [volcano_position, actor_capabilities, selected_dialogue_end]
  writes: [presenter.head, presenter.eyes, presenter.expression, presenter.torso]
  expected_review: [eye_direction_readable, reaction_is_delayed, speech_unchanged]
```

**Again: numbers and keys are invented for design illustration.** An action resolver must bind to a character's actual views, rig and motion vocabulary. It may choose a preauthored clip, generate new pose assets, synthesize procedural motion, blend a limited collection of motion primitives, or ask for a creative substitution when an action is unsupported. This work happens **before deterministic final compilation** if it requires model inference or aesthetic judgment.

### 12.1 Primitive registry design

A promising `AnimationPrimitive` record would declare:

- name, version, namespace and semantic tags (`double_take`, `blink`, `hold`, `reach`);
- accepted actor capabilities and parameter ranges;
- duration model and time influence (including overshoot, decay and continuation);
- preconditions/postconditions for contact and state transitions;
- read/write channels, compositional rules and priority;
- evaluator outputs (`pose_at(t)`, visibility and event markers);
- backend bindings and declared lossy fallbacks;
- expected observable evidence and conformance fixtures;
- possible parameterizable variants with reusable staging and character-specific calibration.

Some primitives will be **composite**: `double_take` expands into hold, glance, head movement, facial switch and camera response. Character-specific calibrations could preserve personality while allowing a general semantic direction. Higher-level `awkward`, `confident`, `sarcastic` are not literal engine primitives; they guide the performance resolver in selecting/parameterizing concrete actions.

### 12.2 Body/face channels and conflicts

A speech gesture may animate the head while `look_at(volcano)` also writes head direction. The compiler must apply a specified rule: sequence, weighted blend, override under a mask, or reject. Two arms may be independent; a hand-grab must coordinate hand position and prop attachment. Blend priorities should not be determined by incidental evaluation order.

A group of characters reacting to an explosion can use staggered delays and individual parameters. But *readability* must be checked at the final camera scale; technically correct eye motion may be invisible in a 9:16 wide shot.

### 12.3 Contact and interaction in 2D

Examples: a character picks up a pointer, leans against a table, points at a diagram or hands something to another character. The performance model should include named attachment points, prop owner, release/acquire events, 2D spatial constraints and a mechanism for pose/IK or explicit clip selection. We do not need general-purpose rigid-body physics to stage those actions, but we do need **consistency of hand-object relationship over time**. A check that a hand belongs to one owner is not proof that its rendered contact looks good.

### 12.4 Audio drives acting—and can be independent

The selected voice waveform is a frozen asset. Useful derived signals include sentence/word/phoneme alignment, speech rhythm, silence and amplitude envelopes. Mouth animation can use coarse open-close states or viseme maps, with confidence and timing caveats. A selected audio line should not be regenerated just because the head turns. Conversely, replacing a voice recording can invalidate viseme animation and speech-dependent camera cues. The harness must keep changes scoped but not ignore actual dependencies.

### 12.5 How generative AI can help without destroying editability

- **Asset generation**: produce sprite sheets, expression variants, background images, props and masks; save chosen outputs and source metadata.
- **Motion proposal**: suggest structured keyframes, choreography, emotion variants, crowd reaction timings.
- **Guided motion extraction**: analyze existing animation references when permitted and convert them to approximate pose/time observations; do not assume recovered parameters are ground truth.
- **Creative search**: generate multiple acting takes and recombine parameter subsets.
- **Criticism**: inspect frames/clips for readability, timing, consistency, identity and awkward composition.

Where a generator yields only a flattened video, use it as a **baked clip** with limited editability. Do not claim that it provides independently movable character bones unless we've actually extracted suitable controls.

### Track 3 questions for later research

- Which 2D actor representations are easiest for AI to author and alter *reliably*?
- Can we generate sufficient sprite poses on demand without persistent identity drift?
- Is a reusable performance library enough to handle the volcano scene, or do we need a new parametric authoring mechanism?
- What does a robust `double_take` contract look like across flat sprites, layered puppets and skeletal rigs?
- How much animation can be evaluated at arbitrary time vs requiring stateful replay?
- What objective checks correlate with humans judging contact, acting, expression and staging?
- Which quality gains result from search over **semantic performance programs** rather than longer prompting?

**Gate:** capability matrix for each actor representation, performance primitive taxonomy, action conflict semantics, timing/audio coupling, validation strategy and reference performance cases. The goal is not to select a rig library prematurely.

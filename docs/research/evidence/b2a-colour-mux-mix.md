# B2a spikes: colour chain, audio/video mux offset, mix chain

Date: 2026-11-14. Throwaway measurement spikes. All spike code and media were deleted after the run; only these results are kept.

## Verdict in brief

| Design claim | Result |
|---|---|
| 1. sRGB frames survive the encode with correct colour | **Holds for pixel values** (flat areas within ±1 of 255 in every channel, in FFmpeg and in Chrome). **But the proposed command does not write the transfer and primaries tags** in FFmpeg 8.1.1; one extra filter fixes it. |
| 2. The mux keeps audio within 5 ms early / 15 ms late | **Holds**: measured offset 0 samples (0.000 ms), also with a concat-built video. Depends on the player honouring the MP4 edit list; ignoring it gives +21.33 ms. |
| 3. Two-pass linear `loudnorm` reaches −14 LUFS and ≤ −1.0 dBTP after AAC, with an exact sample count | **Only partly holds.** Linear mode is refused more often than the design assumes, the guard as proposed did not restore it without extra margin, AAC raised true peak by up to 1.5 dB on peak-limited material (one master ended at −0.6 dBTP), and a decoded AAC track is 512 samples long unless trimmed. |

## Spike 1: colour chain

### Method

- Test chart: 1080×1920 PNG (8-bit RGB, no colour chunks) generated by a Python script. 24 flat patches of 270×240 px in a 4×6 grid, plus a 256-step grey ramp (each step 4 px wide, 480 px tall).
- 30 identical frames piped into FFmpeg (`image2pipe`).
- Decode command, used for every file. It converts with the BT.709 matrix, limited range in, full range out:

  `ffmpeg -i X.mp4 -vf "select=eq(n\,15),scale=in_color_matrix=bt709:in_range=limited:out_range=full:flags=accurate_rnd+full_chroma_int+full_chroma_inp,format=rgb24" -fps_mode passthrough -frames:v 1 X.png`

- Each patch is measured over its interior (32 px inset, 206×176 px). In every file and every patch all pixels in that interior had one identical value, so the numbers below are exact integers, not averages of noise. Frames 0, 15 and 29 were decoded and gave identical results.
- Independent check: the raw Y, Cb, Cr planes of the decoded frame were compared with BT.709 limited-range values computed from the source RGB.

### Finding 1: the proposed command drops two of its four colour tags

The command exactly as proposed produces a file tagged `color_range=tv, color_space=bt709, color_transfer=unknown, color_primaries=unknown`. The H.264 VUI confirms it: `matrix_coefficients=1`, `colour_primaries=2` (unspecified), `transfer_characteristics=2` (unspecified).

In FFmpeg 8.1.1 the output options `-color_primaries` and `-color_trc` are silently overridden by the properties of the frames leaving the filter graph, and a PNG without colour chunks carries "unknown" for both. `-colorspace` and `-color_range` survive only because the `scale` filter sets them on the frames. Proof: the files made with `-color_trc bt709` and `-color_trc iec61966-2-1` were byte-identical (5,914 bytes each).

Three fixes were tested; all give `bt709/bt709/bt709` (or the sRGB transfer when asked):

| Fix | Result |
|---|---|
| Append `,setparams=color_primaries=bt709:color_trc=bt709` to the `-vf` chain | Tags written. Recommended: metadata only, no pixel change. |
| `-bsf:v h264_metadata=colour_primaries=1:transfer_characteristics=1:matrix_coefficients=1` | Tags written. |
| Tag the input: `-color_primaries bt709 -color_trc iec61966-2-1` before `-i pipe:0` | Tags pass through to the output. The output `-color_trc` option is then ignored, so the file carries the input's transfer tag. |

Corrected encode command used for the rest of the spikes:

```
ffmpeg -f image2pipe -framerate 30 -c:v png -i pipe:0 -vf "scale=in_color_matrix=bt709:out_color_matrix=bt709:out_range=limited:flags=accurate_rnd+full_chroma_int,format=yuv420p,setparams=color_primaries=bt709:color_trc=bt709" -c:v libx264 -preset medium -crf 18 -profile:v high -color_range tv -colorspace bt709 -color_primaries bt709 -color_trc bt709 -an out.mp4
```

The pixel data of the as-proposed file and the corrected file are identical (raw YUV planes compared byte for byte).

| JPEG q95 + proposed JPEG chain | `scale=in_color_matrix=bt601:in_range=full:out_color_matrix=bt709:out_range=limited:flags=accurate_rnd+full_chroma_int,format=yuv420p` | 2 | 0.222 | UI orange 253,87,34 | 1 / 0.141 |

Notes:

- The proposed chain's file YCbCr values are within 0.49 of the ideal BT.709 values for every patch, which is plain 8-bit rounding. The ±1 RGB errors are that rounding and nothing else. The ramp is monotonic, 0 decodes to 0 and 255 to 255.
- **The naive chain is not wrong on this FFmpeg.** In FFmpeg 8.1.1 the output options `-colorspace bt709 -color_range tv` constrain the automatic conversion, so it uses the BT.709 matrix (max error 2). The classic error only appears when no colour options are given, or on an FFmpeg that treats `-colorspace` as a tag only. In that case the data is BT.601 and a player reads it as BT.709: greys are untouched, pure green loses 39 levels (0,255,0 becomes 0,216,0), magenta gains 39 in green, skin tones shift by 3 to 7, UI blue by 11.
- By channel, the BT.601-as-BT.709 error is mostly in green: mean 8.75 (G), 1.63 (R), 1.17 (B).
- The JPEG at quality 95 on its own (decoded by Pillow) is within 1 level on the patches (mean 0.181). The proposed JPEG chain adds almost nothing. The naive JPEG chain renders everything about one level dark (ramp 0 decodes to 0.33, 255 to 254.33) and FFmpeg prints "deprecated pixel format used, make sure you did set range correctly".

### Chrome display

Chrome video capture works headlessly. Method: a local HTTP server, a page with a 1080×1920 `<video>` at device scale factor 1, seek to 0.5 s, wait for `seeked` plus two animation frames, then `Page.captureScreenshot` (PNG). A canvas `drawImage` + `getImageData` readback gave values identical to the screenshot in every case. Control: the chart PNG shown in an `<img>` screenshots with zero error, so the screenshot path itself is exact. `requestVideoFrameCallback` did not fire on a paused, seeked video within 1.5 s; the `seeked` event was enough.

If Cutroom ever renders frames that contain a `<video>` element, the GPU setting of the render host changes the colours.

### Limits of spike 1

- Flat patch interiors only. With 4:2:0 chroma, colour bleeds across edges between saturated patches: over the whole frame including edges, 1.96% of pixels differ by more than 2 levels and the worst pixel by 130 (JPEG chain: 2.56% and 141). This is inherent to `yuv420p`, not a matrix error.
- A static image at CRF 18. Motion, gradients with noise and fine text were not tested.
- One decoder (FFmpeg) and one browser (Chrome 157 on Windows). No phone, Safari, or platform re-encode was tested. How a platform treats missing transfer and primaries tags is unknown, which is the reason to write them.
- The chart was generated in Python, not captured from Chrome, so this does not test Chrome's own screenshot colour for CSS content beyond the `<img>` control.

## Spike 2: audio/video mux offset

### Method

- Video: 300 frames, 1080×1920, 30 fps, frame 150 white and all others black, encoded with the corrected chain above.
- Audio: 48 kHz stereo 16-bit WAV, exactly 480,000 samples, silent except one sample at 0.9 full scale at index 240,000. A second file used a 1 ms noise burst (48 samples) at the same place.
- Mux: `ffmpeg -i video.mp4 -i mix.wav -map 0:v:0 -map 1:a:0 -c:v copy -c:a aac -b:a 192k -movflags +faststart out.mp4`
- Audio decode: `ffmpeg -i out.mp4 -map 0:a:0 -ar 48000 -c:a pcm_s16le dec.wav`, and again with `-ignore_editlist 1` before `-i`.
- Offset: FFT cross-correlation of the decoded track against the original over the full length, peak located to one sample and refined by parabolic interpolation. Resolution: 1 sample = 0.0208 ms; the sub-sample estimate was stable to 0.001 sample.
- Video: every frame decoded, `showinfo` timestamps and mean luma read, to find the white frame.

### Results

| Case | Lag (samples) | Lag (ms) | Decoded samples | White frame |
|---|---|---|---|---|
| Click at 240,000 | **0** (sub-sample +0.001) | **0.000** | 480,256 (+256) | frame 150 at 5.000000 s |
| 1 ms burst at 240,000 | 0 (−0.001) | 0.000 | 480,256 | same |
| Click moved +20 ms (sample 240,960), measured against the unmoved reference | **+960** | **+20.000** | 480,256 | same |
| Click moved −50 ms (sample 237,600), measured against the unmoved reference | **−2,400** | **−50.000** | 480,256 | same |
| Video built from three stream-copied 100-frame segments (concat demuxer) | **0** (+0.001) | **0.000** | 480,256 | frame 150 at 5.000000 s |
| Same file, edit list ignored (`-ignore_editlist 1`) | **+1,024** | **+21.333** | 481,280 (+1,280) | not affected |

The method recovers both deliberate offsets exactly, so a zero reading is a real zero. Normalised correlation peak was 0.935 (click) and 0.942 (burst); the decoded click has its largest sample exactly at index 240,000, with AAC pre- and post-ringing from about sample 239,979 to 240,052.

`ffprobe` and container details for `out.mp4` (identical for the concat variant):

| Item | Video | Audio |
|---|---|---|
| `start_time` | 0.000000 | 0.000000 |
| `duration` | 10.000000 | 10.000000 (`duration_ts` 480,000) |
| Packets / frames | 300 | 470 AAC frames |
| Media duration in the track header | 153,600 / 15,360 = 10.000 s | 481,024 / 48,000 = 10.021333 s |
| Edit list | present: media_time 1,024 (two frames of B-frame reorder delay at 1/15,360), duration 10,000 ms | present: media_time 1,024 samples (AAC priming), duration 10,000 ms |
| First packet | pts 0 | pts −1,024, flagged discard, `skip_samples=1024` |
| Last packet | 9.966667 s | pts 479,232, duration 768 |
| Frame spacing | constant 512 ticks (1/30 s) for all 300 frames, including across the concat joins | |

- The audio track holds 1,024 priming samples plus the 480,000 real ones, padded to 470 full AAC frames (481,280). The edit list removes the priming on decode, so the click lands on the exact sample.
- **The decoded track is 480,256 samples, not 480,000.** FFmpeg's decoder does not trim the 256 padding samples at the end, even though the container says 480,000. In this test the extra 256 samples were digital silence.
- Segment joining did not change the offset: the concat output has 300 frames, constant spacing, the white frame at 5.000 s, and the audio lag is still 0.

### Limits of spike 2

- Measured with FFmpeg's demuxer and decoder only. A player that ignores the edit list plays audio 21.33 ms late, which is outside the 15 ms budget. No player or browser playback offset was measured.
- The three segments were encoded with identical settings, were exactly 100 frames each and had no audio of their own. Segments with different encoder settings, odd lengths or their own audio tracks were not tested.
- Offsets come from the container timestamps and decoded samples. The spike says nothing about lip-sync errors made earlier, when the mix is built.

## Spike 3: the mix chain

### Method

Five synthetic 48 kHz stereo pre-masters, each exactly 960,000 samples (24-bit WAV), made with a fixed random seed. Three were asked for; (d) and (e) were added because the first three left questions open.

| Pre-master | Content | `ebur128`: I / LRA / true peak |
|---|---|---|
| (a) speech over music | Noise bursts 300–3,400 Hz with 4.3 Hz syllable modulation, 1.5 to 2 s bursts and 1.5 s pauses, over a quiet chord | −15.7 LUFS / 1.3 LU / −4.8 dBTP |
| (b) loud, dense | Wide-band noise, 55 Hz bass and tones, soft-clipped, with 2 Hz pumping | −2.4 / 0.1 / +1.0 |
| (c) quiet, sparse | Five decaying notes with long gaps and one 4 ms transient at −3 dBFS | −30.2 / 3.6 / −0.8 |
| (d) steady control | Constant-level dense noise and tones | −5.0 / 0.0 / −3.2 |
| (e) spiky speech | As (a), with 3 ms plosive spikes at syllable onsets, to give a realistic speech crest factor | −19.1 / 1.3 / +0.2 |

Commands:

- Pass 1: `ffmpeg -i in.wav -af loudnorm=I=-14:TP=-1.5:LRA=11:print_format=json -f null -`
- Pass 2: `ffmpeg -i in.wav -af "loudnorm=I=-14:TP=-1.5:LRA=<L>:measured_I=..:measured_TP=..:measured_LRA=..:measured_thresh=..:offset=..:linear=true:print_format=json,aresample=48000" -c:a pcm_s24le master.wav`, with `<L>` the measured LRA rounded up to a whole number (minimum 1).
- Guard, placed in front of `loudnorm` in both passes: `aresample=192000,alimiter=limit=<ceiling>:level=false:latency=true,aresample=48000`
- Independent check of every output: `ffmpeg -i X -af ebur128=peak=true -f null -` (integrated loudness, LRA and true peak, 0.1 resolution), and `ffprobe` for the sample count.
- AAC: `ffmpeg -i master.wav -c:a aac -b:a 192k -movflags +faststart master.mp4`

### Two-pass results without the guard

| Pre-master | Pass 1: I / TP / LRA / threshold | Gain needed | Peak after gain | Pass 2 type | `loudnorm` reports I / TP | `ebur128` measures I / TP | Samples |
|---|---|---|---|---|---|---|---|
| (a) | −15.72 / −4.75 / 1.30 / −27.42 | +1.72 dB | −3.03 dBTP | **linear** | −13.95 / −3.05 | −14.0 / −3.0 | 960,000 |
| (b) | −2.46 / +0.96 / 0.00 / −12.46 | −11.54 | −10.58 | **dynamic** | −14.00 / −10.61 | −14.0 / −10.7 | 960,000 |
| (c) | −30.91 / −0.84 / 8.60 / −44.98 | +16.91 | +16.07 | **dynamic** | −14.00 / −1.50 | −14.0 / −1.5 | 960,000 |
| (d) | −5.04 / −3.21 / 0.00 / −15.04 | −8.96 | −12.17 | **dynamic** | −14.00 / −12.16 | −14.0 / −12.2 | 960,000 |
| (e) | −19.18 / +0.24 / 1.30 / −30.89 | +5.18 | +5.42 | **dynamic** | −13.61 / −1.50 | −13.6 / **−0.7** | 960,000 |

Every output had exactly 960,000 samples at 48 kHz, in linear and in dynamic mode.

Three things here contradict the design's assumptions:

1. **A measured LRA of 0.00 forces dynamic mode.** (b) and (d) need only a gain cut and have plenty of peak room, yet pass 2 reported `dynamic`. `loudnorm` treats `measured_LRA=0` as "not supplied". Passing `measured_LRA=0.01` instead gave `linear` for both, with `ebur128` reading −14.0 LUFS. A dense, constant mix can therefore fall into dynamic mode silently. Fix: floor the measured LRA at 0.01 before pass 2.
2. **Linear mode is refused whenever true peak minus integrated loudness exceeds 12.5 dB** (that is, −1.5 − (−14)). (a) is at 11.0 dB and passes. (e), with a speech-like crest factor, is at 19.4 dB and fails; (c) is at 30.1 dB. Real voice-over is normally well above 12.5 dB, so the guard would be the normal path, not the exception.
3. **Dynamic mode's own peak figure cannot be trusted after the final resample.** For (e), `loudnorm` reported −1.50 dBTP but the 48 kHz file measures −0.7 dBTP, and loudness landed at −13.6, not −14. Dynamic mode also changed the dynamics of (c): LRA went from 8.6 (as `loudnorm` measured it) to 18.3.

### The guard

Ceiling as proposed: −1.5 dBTP minus the gain from pass 1, with no margin. Where that failed, the ceiling was lowered in steps until pass 2 reported linear.

| Pre-master | Margin | Ceiling (dBFS) | Re-measured I / TP | New gain | Peak after gain | Pass 2 | `ebur128`: I / TP |
|---|---|---|---|---|---|---|---|
| (c) | 0 (as proposed) | −18.41 | −31.06 / −18.37 | +17.06 | −1.31 | **dynamic** | −14.2 / −1.5 |
| (c) | 0.1 dB | −18.51 | −31.06 / −18.47 | +17.06 | −1.41 | dynamic | −14.2 / −1.5 |
| (c) | 0.2 dB | −18.61 | −31.06 / −18.57 | +17.06 | −1.51 | **linear** | **−13.3** / −1.5 |
| (e) | 0 (as proposed) | −6.68 | −19.87 / −5.99 | +5.87 | −0.12 | **dynamic** | −13.4 / −0.9 |
| (e) | 0.1, 0.2, 0.5, 1.0 dB | −6.78 to −7.68 | I −19.88 to −19.95, TP −6.09 to −6.99 | +5.88 to +5.95 | −0.21 to −1.04 | dynamic (all four) | −13.3 to −13.4 / −0.9 |
| (e) | 2.0 dB | −8.68 | −20.02 / −7.99 | +6.02 | −1.97 | **linear** | −13.9 / −2.0 |

- **The guard as proposed did not achieve linear mode in either case.** Two effects work against it. Limiting lowers the loudness, so the gain needed afterwards is larger (by 0.15 dB for (c), 0.69 dB for (e)). And the limiter holds its limit exactly at 192 kHz (verified: peak equals the limit to 0.01 dB), but resampling back to 48 kHz rebuilds peaks: on (e) the 48 kHz file peaked 0.65 dB above the limit, true peak 0.69 dB above.
- Linear mode was reached once the ceiling had enough margin: 0.2 dB for (c), 2.0 dB for (e). A single fixed margin is not safe; the guard needs a loop (limit, re-measure, lower the ceiling by the shortfall, repeat) or a generous margin.
- The guard keeps the sample count (960,000) and the timing (cross-correlation lag against the source: 0 samples) with `latency=true`.
- `alimiter` rejects `limit` below 0.0625 (−24.08 dBFS): "Value 0.050000 for parameter 'limit' out of range [0.0625 - 1]". The guard as written therefore cannot be used when the gain needed exceeds about 22.6 dB. Applying the gain before the limiter would avoid this; that variant was not tested.
- **On the sparse pre-master, linear mode missed the loudness target by 0.7 LU** (−13.3 LUFS by `ebur128`). The cause is the pass 1 measurement: `loudnorm` reads (c) as −30.91 LUFS and LRA 8.6 where `ebur128` reads −30.2 and 3.6. Resampling to 192 kHz first does not change the `ebur128` reading, so the two meters simply disagree on sparse material. On (a) and (e) they agree to 0.1. In linear mode `loudnorm`'s reported output true peak is also unreliable (it said −3.34 dBTP for a file that measures −1.5).
- Extra test: measuring the guarded signal with `ebur128` and applying a plain `volume` gain gave −14.0 LUFS for both (c) (true peak −2.2) and (e) (true peak −2.0), 960,000 samples. That is a linear master with no `loudnorm` in the second pass, and it did not show the 0.7 LU miss.

- **Loudness survives AAC** within 0.2 LU.
- **True peak does not.** AAC raised it by 1.4 to 1.5 dB on the spiky speech and by about 3 dB on the dense clipped mix. The guarded linear master of (e) left at −2.0 dBTP and came back at −0.6 dBTP, which breaks the ≤ −1.0 dBTP claim even though the master was 0.5 dB under its own ceiling. A master sitting exactly at −1.5 dBTP would have come back near −0.1. The 0.5 dB between the −1.5 master ceiling and the −1.0 delivery limit is not enough for this kind of material; the dynamic-mode fallback ended above full scale (+0.8 dBTP).
- **Sample count.** Each file has 939 AAC frames = 961,536 samples: 1,024 priming samples at the start and 512 padding samples at the end. The MP4 carries an edit list (media_time 1,024, duration 20,000 ms) and `ffprobe` reports `duration_ts=960000`. On decode FFmpeg removes the priming (lag against the master: 0 samples) but not the padding, so a plain decode gives **960,512 samples**. The extra tail is low-level codec decay, not silence (up to 0.037 of full scale on the dense mix, about 0.0005 on the others). Decoding with `-af atrim=end_sample=960000`, or with `-t 20` as an input option, gives exactly 960,000.

### Limits of spike 3

- Synthetic signals, 20 s each. No real voice-over or music was measured. The crest-factor argument (linear needs true peak minus loudness ≤ 12.5 dB) is arithmetic from `loudnorm`'s rule and was confirmed on three signals; how often real Cutroom mixes cross it was not measured.
- (b) is far louder than a normal pre-master (−2.4 LUFS). It was kept because it exposes the LRA 0.00 behaviour and the largest AAC peak growth.
- One AAC encoder (FFmpeg native) at one bitrate. Peak growth with another encoder or bitrate was not measured.
- `ebur128` reports to 0.1 LU and 0.1 dB, so the "−14.0" figures are −14.0 ± 0.05 at best.
- LRA on the sparse signal is unstable (3.6 by `ebur128`, 8.6 by `loudnorm`, about 19 after the guard) because very few blocks sit above the gate. Do not read meaning into those LRA values.
- The guard loop that would be needed (limit, re-measure, lower ceiling, repeat) was stepped by hand, not built or tested for convergence.
- The ducking test used one key level per row and steady noise as speech. Real speech with wide level swings will pump more.

## What failed or surprised

1. The proposed encode command leaves `color_transfer` and `color_primaries` unknown on FFmpeg 8.1.1. Add `setparams=color_primaries=bt709:color_trc=bt709`.
2. The "naive" chain is correct on FFmpeg 8.1.1 as long as `-colorspace bt709 -color_range tv` are present, because those options now steer the conversion. The 39-level error belongs to the case with no colour options, or to an older FFmpeg.
3. Chrome with `--disable-gpu` shows BT.709 video up to 12 levels off in blue.
4. `requestVideoFrameCallback` did not fire for a paused, seeked video in headless Chrome; `seeked` was sufficient.
5. `loudnorm` falls to dynamic mode when the measured LRA is 0.00.
6. The limiter guard as proposed did not restore linear mode; it needed 0.2 dB and 2.0 dB of extra margin in the two cases tried, and it cannot be configured at all below −24.08 dBFS.
7. `loudnorm` linear mode missed −14 LUFS by 0.7 LU on the sparse signal because its pass 1 meter disagrees with `ebur128`.
8. AAC raised true peak by up to 1.5 dB on peak-limited material; one guarded linear master ended at −0.6 dBTP.
9. A decoded AAC track is longer than its source by the end padding (256 samples at 10 s, 512 at 20 s) unless trimmed.

## 2. One decision across M4 and M6: C1

These six parts answer M4 O1, M4 O3, M6 O1, M6 O3, M6 O4 and M6 O5 together, so that the harness and the quality system stay consistent from M4 to M6.

### C1.1 How a run ends, before and after `delivery_finalize` is complete (M4 O1)

**Decision.**

- **From M6-09** the tool is the designed chain (`lld/07` D4; `lld/09` §3.6, §4). Production ends when the chain's deliverable record is `delivered` or `delivered_with_limitations`. A `blocked` or `incomplete` record wakes the Director at once ("a hard check failed on an export", `lld/07` D2), and the Director then repairs or calls `director_report_blocked`. The tool result states `completion_state` and never calls such an export delivered (D10; `lld/11` §13 #13).
- **At M4 and M5** a staged `delivery_finalize` keeps the designed name, input (`delivery_profile`, `expected_head`), head check and immediate errors (`STALE_BASE`, `NOT_READY`). It compiles inline in `frozen` mode at **grade `preview`, rung `final`**, and it also requires every pinned commitment to be `frozen`, returning `NOT_READY` otherwise. It then calls `plan_to_jobs(plan, "review")`, which renders the final-rung chunks and runs `film.concat`, plus `audio.mix` and `film.mux` only when the plan has audio. It writes no deliverable record and returns no `completion_state`. Its result names the file and the plan's grade and says that this build has no final-file check, review or record yet; the CLI shows "exported, not checked: not a delivery". The run ends when this chain returns a file. A failed chain wakes the Director, as at M6.

**Why.**

- R5 refuses delivery below grade `final`: "For `delivery` the adapter refuses a plan unless its rung and its grade ... are both `final` and every pinned commitment is `frozen`" (`lld/06` §2.4). Grade `final` needs "every asset is `eligible` for the delivery profile" (`lld/05` D4). Font faces are `asset` entities (`lld/04` §2.2, `font.faces[].file`), and only M6-04's rule table may write `rights.status` (FR1). Before M6, then, a single line of on-screen text would make the M4 film `NOT_READY` with `RIGHTS_UNRESOLVED`. M5-10(c) already compiles its narrated film at grade `preview`, rung `final` for the same reason, so this makes M4 and M5 alike.
- Requiring frozen commitments keeps the rung-`final` chunks out of R5's speculative hold (an `expensive` job on a `provisional` commitment waits in `declared`, `lld/06` §2.9), and it makes the Director practise the M6 rule early.
- The other two options in M4 O1 are rejected. A park after a `final` render cannot be told apart from a stall (D2). Ending with `director_report_blocked` would make a successful run look blocked.

**Consistent with:** `lld/07` D2, D4, D10; `lld/11` §13 #13; `lld/06` §2.4, §2.9; `lld/05` D4; M5-10(c).
**Documents that would change:** `lld/11` (one build-revision row stating the staged form and when it ends). In `impl`: M4-09 "Build", M4-13 test 5 (grade `preview`), and M4-03 and M4-07, because for `delivery_finalize` the end of the run depends on the chain's outcome and is not a flag fixed on the call. No stage LLD changes: the M6 form is the designed one.
**Confidence:** medium. The alternative is to pull M6-04's authored-only rights seed forward to M4, which waits on M6 O6b.

### C1.2 How treatments are submitted (M4 O3)

**Decision.**

- The treatment worker's only tool is **`submit_treatments`**, with effect `propose`. Its input is typed to every leaf and has no tight length limits. It holds `treatments`, a list of exactly the requested number of R3 `treatment` field sets (`premise`, `hook`, `structure`, `visual_approach`, `tone[]`, `techniques[]`, `risks[]`), and `differences`, a list of `{a, b, difference}` in which `a` and `b` index `treatments`, with one entry for each unordered pair.
- The handler checks the count and that every pair has exactly one difference, and returns `SCHEMA_INVALID` naming the missing or repeated pair otherwise. It then writes the treatments with `status: proposed` as the worker's patch proposal and stores the differences in the worker's Diagnostic Evidence Bundle (`WorkerOutcome.evidence_bundle`), keyed by the new treatment handles. The Director's notice references both. No field is added to `treatment`.
- M4-13 test 6 and acceptance case A14 read the differences from that bundle. The Director's later `decision` lists the alternatives and why they lost, as designed.

**Why.** G17 already gives "every sub-loop submission tool" the `propose` effect, and D5 ends every structured sub-loop with a `submit_*` call, which batch 2c verified (26 of 30 and 25 of 30 runs ended with a valid call unaided, `lld/11` §12.3). A difference describes a pair, so it belongs to no single `treatment`; a worker's supporting output already goes in its evidence bundle (D6.1). A fully typed input travels as a structured argument on MiniMax (J1), and the conformance test covers it (J4).
**Documents that would change:** `lld/07` D4 (the Delegation rows) and the G17 list in `lld/11`, adding the name as a build revision, because R6 owns tool names.
**Confidence:** medium (the name and the home of the differences are choices; the mechanism is designed).

### C1.3 Which evidence delivery requires (M6 O1)

**Decision.** Code computes the required set for an export from the installed check catalogue (`quality_settings@1`) and the plan's closure:

1. **Every hard check:** R-01; K-01 when an essential claim is in the closure; K-05; F-01 to F-07; F-09. Each must be `PASS`. A hard check whose scope has no subject in the closure is recorded `NOT_APPLICABLE` (K-05 with no `evidence` media need; F-08 while embedded labelling is off, U7).
2. **Every check named by a hard constraint's proof** (F-06's inputs, C1.5), and the reviewer votes of C1.6.
3. **Every corrective check whose scope has a subject in the closure.** For the thin film these are C-00 to C-05 and C-07 for each component, P-07 and M-05 for each shot, A-01 for each selected take, and M-04 and A-03 for the film. An open failure or an `UNKNOWN` among them gives `needs_material_revision` (`lld/09` D2, §3.6).
4. **The T7 review of the exported file** (F-07).

`delivery_finalize` requests every missing record as a `check.run` job; records that already exist are cache hits. A record that cannot be produced is `UNKNOWN`. A check absent from the installed catalogue (at M6: K-02, K-03, K-04, P-11 and S-01) is not required; where its scope has a subject in the closure, the deliverable record's `known_limitations` names it, for example "K-02 was not run: not in this build". Observational checks are never required.

**Why.** R9 blocks when "evidence that delivery requires is missing" (`lld/09` §3.6) but never lists it. `lld/11` §10 #144 says the revalidation checks "are not required for promotion, and delivery requires them", and R5 says the handler "adds the `check.run` and review jobs that depend on `film.mux`" (`lld/06` §2.4). Naming what was not run follows D10's practice for audio nobody heard.
**Caution from V1.** On correct takes of short lines with numbers, times, abbreviations and names, Whisper gave a normalised WER of 0.08 to 0.30, above A-01's 0.10 (`research/evidence/v1-openrouter-kokoro-and-alignment.md` §4.5). Before A-01 can gate delivery, M5-09's normaliser must cover the kinds of difference V1 lists ("7:45" against "7.45", "U.N." against "UN", lexicon names, spelling variants), or `R9-3` must move `stt.wer_max_take`. Otherwise correct films stall in `needs_material_revision`.
**Documents that would change:** `lld/09` §3.6 (a "Required evidence" paragraph) and §3.7 (`known_limitations`); `lld/11` (one row).
**Confidence:** high.

### C1.4 When finalising is a stop (M6 O4)

The accepted HLD already counts the Director's judgement as a stop: "Deliver: The eligible candidate is accepted, the expected marginal benefit of further work does not justify latency/cost/regression risk (or the optional improvement budget is used), and exported-file validation passes" (`hld/02` B3.5). R9 §3.6 lists only the four mechanical conditions, which are upper bounds that end optional polish. So calling `delivery_finalize` on an `eligible` candidate is the stop condition. The automatic export when the budget runs out (`lld/09` §3.6, "Budget") is also one. The call is a fact in the audit log written by the harness, not a field the Director can write, so D9 still holds. R9 §3.6 should say so in one sentence.

### C1.5 How F-06 evaluates a proof by kind (M6 O3)

**Decision.** F-06 passes when the proof of every Quality Intent hard constraint is `PASS`, evaluated as follows:

- **`{by: check, check: X}`** with X other than F-06: the validation record of X on the exported file or its closure. X joins the required set (C1.3).
- **`{by: check, check: "F-06"}`**, allowed only for kinds `duration`, `aspect` and `language`. F-06 evaluates the constraint itself from the exported file and the plan, as `lld/11` §13 #33 already has it do for duration ("A hard duration limit exists only as a Quality Intent hard constraint, checked by F-06"). The `params` shapes are: `duration` `{max_s?, min_s?}`, compared with the file's duration N·T; `aspect` `{w, h}`, compared with the file's displayed width and height (ffprobe, with the sample aspect ratio); `language` `{code}`, compared with the `language` of every `voice_line` and `caption_track` in the closure.
- **`{by: reviewer, ...}`**: the vote verdict of C1.6.

The other kinds map onto checks that already exist: `rights_scope` to R-01; `essential_claim` to K-01 (and K-02 from M8); `must_include`, `must_not_include` and `custom` to a named check where one proves the constraint, otherwise a reviewer proof. A proof that names a check absent from the installed catalogue, or names F-06 for any other kind, is refused when the Quality Intent is written ("Every hard constraint names its proof, so none is unprovable", `lld/09` §3.4); R3, which owns the code, chooses it. No new check IDs are added, which avoids crossing R3 and R9's canonical catalogue.
**Documents that would change:** `lld/09` §3.1 (F-06 row) and §3.4 (`params` for three kinds); `lld/04` §2.2 (`quality_intent`); `lld/11` (one row).
**Confidence:** medium.

### C1.6 How the three-vote rule decides (M6 O5)

**Decision.** A first `PASS` stands. After a first `FAIL` or `UNKNOWN`, up to `review.hard_proof_votes` − 1 further reviews run, each a fresh Reviewer sub-loop on the same pinned bundle (`lld/07` D6.4), and they stop as soon as one value holds a strict majority of `review.hard_proof_votes`. **The verdict is the value with a strict majority; with no strict majority, for example `FAIL`, `PASS`, `UNKNOWN`, it is `UNKNOWN`.** A `NOT_APPLICABLE` answer to a hard-proof question counts as `UNKNOWN`, because a hard constraint applies by definition. Either `FAIL` or `UNKNOWN` leaves F-06 failing and the state `blocked`. The validation record keeps every vote, which G13's calibration on "the share of split votes" needs. Votes on a proof evaluated at T7 belong to T7: they sit outside the per-cycle cap and are paid from the delivery reserve (`lld/09` §3.3), so a cap cannot block delivery; if the reserve cannot pay for them, the verdict stays `UNKNOWN`. A human may adjudicate (FR4).
**Why.** It follows R9 D1 ("its verdict is `UNKNOWN`, never `PASS`") and FR4, and it works for any odd value of the `human` setting.
**Documents that would change:** `lld/09` §3.4 (last paragraph); `lld/07` D6.4 (one sentence).
**Confidence:** high for the verdict rule; medium for the cap and the reserve.

## 6. Other findings outside the listed points

These came up while reading the design and the V1 evidence; each touches a work package in these milestones.

1. **M5-02's format check would fail.** V1 has already measured the PCM format: signed 16-bit little-endian, 24,000 Hz, mono (V1 §2.2, §2.3), which settles the format part of U18 (6). M5-02 plans to check PCM against an MP3 of the same text "within the MP3's priming and padding", but the MP3 timeline gains about 85 ms of silence at each sentence join (V1 §2.4), so the check fails on any line of more than one sentence. Record V1's result and cross-check single-sentence lines only, or drop the check. M5-02's test that "no request body carries a field beyond the four" must also allow the `provider` field if pinning is adopted (M5 O8a).
2. **Kokoro's takes are not byte-repeatable.** Timing repeated exactly but the waveform did not (V1 §2.6), and a different provider gives a different take. This matches the design's `variant` rule for engines that are not repeatable, but it confirms that a lost take cannot be re-fetched bit for bit. Spooling the bytes before confirmation (M5-02) is therefore essential, and with `X-Generation-Id` spooled, `reconcile` can confirm whether a call was billed through the generation look-up instead of answering `cannot_tell`.
3. **F-02 depends on a field that does not exist.** F-02 passes "when the profile needs audio" (`lld/09` §3.1), but `delivery_profile` has no field saying whether audio is needed. U2 allows a film with no music, and the abstract brief has no narration, so that film will need the field before it is delivered (M11 at the latest). M4 is not affected (C1.1).
